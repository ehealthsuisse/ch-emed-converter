# Feature Specification: CH EMED EPR, further document types (DIS, PADV, PML)

**Feature Branch**: `005-epr-dis-padv-pml`

**Created**: 2026-11-10

**Status**: Draft

**Input**: User description: "CH EMED EPR, weitere Dokumenttypen: Der Converter soll die in Feature 004 zurückgestellten Dokumenttypen von CH EMED EPR 3.0.0 (ch.fhir.ig.ch-emed-epr) unterstützen: Abgabe (DIS), pharmazeutische Empfehlung (PADV) und Medikationsliste (PML), jeweils zwischen dem allgemeinen CH EMED IG 6.0.0 und CH EMED EPR, gemäss Conversion Scope der Constitution 1.5.0 und mit derselben Infrastruktur wie Feature 004 (Hub CH EMED, Entfernen und Ausweisen nicht unterstützter Elemente, Profilwechsel, Validierung gegen die gepinnten Profile). Die Medikationsliste wird im EPD von der Plattform erzeugt; ob neben EPR → CH EMED auch CH EMED → EPR nötig ist, ist zu klären. Ebenso zu klären: ob und wie DIS, PADV und PML über CH EMED nach CHMED16A gelangen (eMediplan kennt nur Medikationsplan und Rezept), und welche Referenzen (Behandlungsplan, Rezept, Abgabe) beim Umwandeln geprüft oder ergänzt werden. Ausgaben müssen fehlerfrei validieren; nicht unterstützte Elemente werden im Report ausgewiesen, nie still verworfen. Transport ins EPD bleibt ausser Scope. Verfügbar über Library, CLI und REST mit identischem Verhalten; Capabilities nennen die neuen Dokumenttypen. Testkorpus: die offiziellen Beispiele von CH EMED und CH EMED EPR für diese Typen."

## Clarifications

### Session 2026-11-10

- Q: In the EPR the medication list is generated by the community's aggregation service, which must be its author (a Device). Should general CH EMED medication lists be converted to PML? → A: Both directions, but CH EMED → PML only for lists whose author is a Device, as for PMLC (feature 004, research F8); lists read from the EPR convert there and back, others fail with `MISSING_REQUIRED_DATA` at the author.
- Q: eMediplan knows only medication plans and prescriptions. What happens to CH EMED dispenses, pharmaceutical advice and medication lists converted to CHMED16A? → A: Refused as unsupported document type, naming the supported types (medication card, prescription); documented as capability gap. The existing behaviour stays.
- Q: How are references to other documents (treatment plan, prescription, dispense, advice) handled? → A: Kept unchanged; a dispense without treatment-plan reference gets it from the existing option of feature 004, otherwise `MISSING_REQUIRED_DATA`. In addition, the converter checks that the references within one document agree with each other and with the entries of the same document, and reports contradictions; it does not check whether referenced documents exist outside the document.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Read dispenses, pharmaceutical advice and medication lists from the EPR (Priority: P1)

A primary system (pharmacy system, practice software, hospital system) has retrieved a dispense (DIS), a pharmaceutical advice (PADV) or the patient's medication list (PML) from the EPR of the CARA community. It converts the document to the general CH EMED document of the same type, to use it in the system or pass it on.

**Why this priority**: Reading is what every care provider does with these documents; the medication list in particular is the EPR's complete view of the patient's medication. Reading needs no data beyond the source and, as for feature 004, should lose no clinical data, because every CH EMED EPR document is also a CH EMED document.

**Independent Test**: Convert the official DIS, PADV and PML examples of CH EMED EPR 3.0.0 to CH EMED; the CH EMED documents validate against the pinned CH EMED profiles.

**Acceptance Scenarios**:

1. **Given** a valid DIS document, **When** it is converted to CH EMED, **Then** the result is a valid CH EMED Medication Dispense document with the same dispense, its treatment-plan reference and, where present, its prescription and pharmaceutical-advice references, and the report lists every element that was changed.
2. **Given** a valid PADV document (for example a change, a cancellation or a comment), **When** it is converted to CH EMED, **Then** the result is a valid CH EMED Pharmaceutical Advice document with the same observation, the same changed medication statement or medication request, and the same references.
3. **Given** a valid PML document with medication statements, requests, dispenses and observations, **When** it is converted to CH EMED, **Then** the result is a valid CH EMED Medication List document with the same entries in the same order.
4. **Given** a PML document without entries, **When** it is converted to CH EMED, **Then** the result is a valid Medication List without entries.
5. **Given** a document that does not conform to CH EMED EPR, **When** it is converted from CH EMED EPR, **Then** the conversion fails with the validation findings and produces no output.

---

### User Story 2 - Create EPR dispenses and pharmaceutical advice (Priority: P1)

A pharmacy system documents a dispense or a pharmaceutical advice as a general CH EMED document and converts it to a CH EMED EPR document, which it then submits to the EPR itself. The converter leaves out what CH EMED EPR does not support, reports it, and asks the caller for the data the EPR requires but the source lacks.

**Why this priority**: Dispenses and pharmaceutical advice are the documents pharmacies contribute to the EPR; without them the medication list in the EPR is incomplete.

**Independent Test**: Convert the official CH EMED dispense and pharmaceutical-advice examples, and synthetic variants, to CH EMED EPR with the required options; every result validates against the pinned CH EMED EPR profiles, and the report lists every removed element.

**Acceptance Scenarios**:

1. **Given** a CH EMED dispense document whose dispense references its treatment plan, **When** it is converted to CH EMED EPR, **Then** the result is a valid DIS document and the report lists the removed elements.
2. **Given** a CH EMED dispense document whose dispense has no treatment-plan reference, **When** it is converted without supplying one, **Then** the conversion fails with `MISSING_REQUIRED_DATA` naming the reference, never a value; **When** the caller supplies it, **Then** the result is a valid DIS document and the report names the supplied reference as derived value.
3. **Given** a CH EMED pharmaceutical-advice document, **When** it is converted to CH EMED EPR, **Then** the result is a valid PADV document with the same observation code, the same changed statement or request, and the same references.
4. **Given** a CH EMED dispense or advice document with elements CH EMED EPR does not support, **When** it is converted, **Then** these elements are left out and reported, clinically relevant ones as clinical loss; with strict mode the conversion fails on clinical loss.
5. **Given** a CH EMED medication list whose author is a Device (for example a list read from the EPR in story 1), **When** it is converted to CH EMED EPR, **Then** the result is a valid PML document; **Given** a medication list with a person as author, **Then** the conversion fails with `MISSING_REQUIRED_DATA` at the author (clarification 2026-11-10).

---

### User Story 3 - Same behaviour through all interfaces (Priority: P3)

The conversions of stories 1 and 2 and the options they need are available through the library, the CLI and the REST service, with identical documents and reports. The capability information names the new document types.

**Why this priority**: Required by the constitution and by feature 004 for every conversion; it follows once the conversions exist.

**Independent Test**: Convert the whole test corpus of this feature through library, CLI and REST and compare documents and reports byte for byte; the capabilities list DIS, PADV and PML for CH EMED EPR.

**Acceptance Scenarios**:

1. **Given** any input of the test corpus, **When** it is converted through library, CLI and REST with the same options, **Then** documents and reports are identical.
2. **Given** the running service, **When** its capabilities are requested, **Then** CH EMED EPR lists the document types PMLC, PRE, MTP, DIS, PADV and PML, each with the directions it supports.

### Edge Cases

- CH EMED EPR or CH EMED document of a type still outside the converter's scope → refused as unsupported, naming the supported types.
- Dispense of a medication without prescription (self-medication, official example UCSF4) → converted; the prescription reference is optional, the treatment-plan reference is not.
- Dispense whose treatment-plan reference is given in the source and also supplied by the caller → the source wins; the supplied reference is an error naming the mismatch, as for feature 004 (FR-017 of feature 004).
- Pharmaceutical advice that cancels or suspends a treatment and therefore carries no changed statement or request → converted; the references identify the affected documents.
- Pharmaceutical advice whose changed medication statement or request contains elements CH EMED EPR does not support → left out of the contained resource and reported, with the path inside the advice.
- Medication list whose author is not a Device → `MISSING_REQUIRED_DATA` at the author on the way to PML (FR-002).
- References to documents the converter does not have (treatment plan, prescription, dispense, advice) → kept as given and not resolved; the converter never contacts the EPR.
- Contradicting references within a document (for example a medication-list dispense pointing to a treatment plan that is not among the list's entries while the list holds it under another identifier, or an advice whose changed statement belongs to another treatment plan than the one it references) → reported as warning with the paths, output unchanged (FR-008).
- Original representation: optional for DIS, PADV and PML; a PDF/A of the source or supplied by the caller is kept, none is rendered, and every case is reported.
- Very large medication list (for example 100 entries of each kind) → converted within the time limits of feature 004.
- CH EMED dispense, pharmaceutical advice or medication list converted to CHMED16A → refused as
  before (eMediplan knows only medication plans and prescriptions); the existing refusal stays and
  its message now names the supported types (clarification 2026-11-10).
- Non-ASCII content (umlauts, accents, French and Italian texts) → preserved.

## Requirements *(mandatory)*

### Functional Requirements

**Conversions**

- **FR-001**: The system MUST convert in both directions between the CH EMED Medication Dispense document and DIS, and between the CH EMED Pharmaceutical Advice document and PADV.
- **FR-002**: The system MUST convert in both directions between PML and the CH EMED Medication List document; CH EMED → PML only for lists whose author is a Device, otherwise the conversion MUST fail with `MISSING_REQUIRED_DATA` at the author (clarification 2026-11-10).
- **FR-003**: Document types outside FR-001 and FR-002 MUST be refused as unsupported with a specific error that lists the supported document types.

**Conformance and fidelity**

- **FR-004**: Every CH EMED EPR output MUST validate without errors against the pinned CH EMED EPR profiles and the profiles they depend on; output failing validation MUST NOT be returned.
- **FR-005**: Every CH EMED EPR input MUST be validated before conversion; an input with errors MUST be refused with the validation findings.
- **FR-006**: Elements that CH EMED EPR does not support MUST be left out of CH EMED EPR output, including inside contained and changed resources, and listed in the report with path and reason; clinically relevant elements MUST be marked as clinical loss.
- **FR-007**: References to other documents (treatment plan, prescription, dispense, pharmaceutical advice) MUST be kept unchanged in both directions. A dispense without a treatment-plan reference MUST get it from the existing treatment-plan reference option of feature 004, reported as derived value; otherwise the conversion MUST fail with `MISSING_REQUIRED_DATA` naming the reference, never its value. The converter MUST NOT check whether referenced documents exist outside the document.
- **FR-008**: The converter MUST check that the references within one document agree: a reference to an entry of the same document (for example in a medication list) MUST resolve, and the references of one dispense or advice (treatment plan, prescription, dispense, changed statement or request) MUST NOT contradict each other or the entries of the same document. Contradictions MUST be reported with the paths of the references concerned, never their values; they are warnings and do not change or fail the conversion, because references are kept as given (clarification 2026-11-10).
- **FR-009**: Data required by CH EMED EPR but missing in the source MUST come from the existing options (patient identifier, author, confidentiality, treatment-plan references); otherwise the conversion MUST fail with `MISSING_REQUIRED_DATA`. No other defaults may be applied to clinically relevant data.
- **FR-010**: Original representations are optional for DIS, PADV and PML: a PDF/A-1 or PDF/A-2 supplied by the caller or present in the source is kept, the supplied one taking precedence; no PDF is rendered; a PDF that is not PDF/A is not used; every case is reported.
- **FR-011**: A round trip CH EMED EPR → CH EMED → CH EMED EPR MUST give the original document apart from the changes documented in the mapping specification; a round trip CH EMED → CH EMED EPR → CH EMED MUST differ only by the elements of FR-006.
- **FR-012**: For identical input and options, output MUST be byte-identical.
- **FR-013**: The rules of every direction MUST be documented in the mapping specification of feature 004 and covered by fixture tests, including all official DIS, PADV and PML examples of CH EMED EPR 3.0.0 and the dispense, advice and list examples of CH EMED 6.0.0.

**Interfaces**

- **FR-014**: All conversions and options MUST be available through library, CLI and REST with identical behaviour and report, without changing the behaviour of existing conversions other than turning the former refusal of these document types into conversions.
- **FR-015**: The capability information MUST list DIS, PADV and PML as document types of CH EMED EPR, and the API description MUST cover them.

**Data protection**

- **FR-016**: Logs, error messages and reports MUST NOT contain patient-identifying data; they reference element paths and resource types, never resource ids or values.
- **FR-017**: The system MUST NOT contact the EPR, CARA's eMedication service or any other external service.

### Key Entities

- **Dispense document (DIS)**: an EPR document recording one dispense of a medication by a pharmacy, always linked to a treatment plan and optionally to a prescription and a pharmaceutical advice.
- **Pharmaceutical advice document (PADV)**: an EPR document recording one advice (for example change, cancel, suspend, refuse, comment) on a treatment plan, prescription or dispense, with the changed statement or request where the advice changes something.
- **Medication list (PML)**: an EPR document generated by the community's aggregation service with the current treatment plans, prescriptions, dispenses and advice of a patient.
- **Document reference**: the identifiers of another EPR document and of its entry that a dispense or advice belongs to; kept as given, never resolved.
- **Conversion report**: as in features 001–004.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% of the official DIS, PADV and PML examples of CH EMED EPR 3.0.0 are converted to CH EMED documents that validate without errors.
- **SC-002**: 100% of the official dispense and pharmaceutical-advice examples of CH EMED 6.0.0 are converted to CH EMED EPR documents that validate without errors when the required data is supplied by options, and fail only for documented missing data without them.
- **SC-003**: 100% of the round trips of FR-011 over the test corpus differ only by documented changes.
- **SC-004**: Converting a medication list with 100 entries, including validation, stays within the time limits of feature 004 on the reference hardware.
- **SC-005**: For 100% of the inputs of the test corpus, library, CLI and REST give identical documents and reports.
- **SC-006**: An automated scan of logs and reports from all test runs finds zero patient-identifying data.
- **SC-007**: During all conversions, no connection to an external service is attempted.
- **SC-008**: The reference check of FR-008 reports no contradiction for any official example, and reports 100% of a set of synthetic documents with one contradicting reference each.

## Assumptions

- This feature builds on feature 004 and reuses its format, options (patient identifier, author, confidentiality, treatment-plan references, original representation), the removal and reporting of unsupported elements, and its mapping specification.
- The pinned versions stay unchanged: CH EMED EPR 3.0.0, CH EMED 6.0.0, CH Core 6.0.0; no new package is needed.
- As for feature 004, every valid CH EMED EPR document is also a valid CH EMED document, so reading mainly changes profile declarations; this is verified against the official examples.
- The list of unsupported elements of feature 004 is extended to the dispense, advice and list profiles in the same way; the review of clinical flags (feature 004, T036) covers the new entries as well.
- A pharmaceutical advice and a dispense concern exactly one medication each, as in the CH EMED documents; the converter does not split or merge documents.
- Submitting documents to the EPR and retrieving them are out of scope (constitution 1.5.0).
- Fixtures contain only synthetic data and the official examples of the IGs (constitution).
- The reference hardware is the one of feature 002 (provisional: 4 vCPU, 8 GB RAM).
